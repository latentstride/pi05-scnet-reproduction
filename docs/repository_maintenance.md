# 仓库维护与分支约定

本约定区分软件维护、研究探索和资源授权。它不改变GitHub设置，也不授予GPU使用或发布权限。

## 分支与审查

|分支|用途|合并前证据|
|---|---|---|
|`main`|经人工审查的代码、协议及可追溯研究记录|相关CPU验证、证据范围、diff审查；研究结果可包含明确标记的失败|
|`fix/*`|针对已定位问题的修复|真实失败复现、正反例、回归、原安全合同是否变化|
|`experiment/*`|探索性模型/控制/规划实验|预先固定变量、初态、预算与停止规则；未验证结果不得晋升|
|`chore/*`|文档、索引、忽略规则和维护工具|不能改变实验执行逻辑或历史数据；检查内部链接与保留范围|

后续通过Pull Request审查后合并。维护者可另行考虑main保护规则；本次未设置保护、删除分支、建Tag、改写历史或自动合并。用户指定的`chore/repository-cleanup`专用于本轮维护，待进行的G2算法修复不混入此分支。

## 版本与实验记录

每个新实验目录建议记录：实际执行源码Commit、发布文件SHA256清单、配置/run lock、模型与上游版本、初态/提示、资源预算、授权依据、作业ID、终态及原始证据存储范围。Git commit、发布包清单哈希、部署目录版本名和用户授权是四种不同标识，不得互相代替。

先写协议与候选配置，得到CPU证据后再提交人工审查。`READY_FOR_REVIEW`只表示可供审查；`submission_allowed=false`不能被维护脚本改为true。预算批准不代表提交批准。历史任务COMPLETED、监督器passed、CPU合成通过和真实任务成功分别记录。

发布快照和历史实跑脚本可与当前源码相同，也可因脱敏或后续修复不同。保留其原路径与原清单；不以“最新版文件”覆盖旧运行包。公开副本的脱敏SHA与原始运行文件SHA分别解释。

## 数据和敏感文件

模型、原始数据、完整轨迹、认证文件、环境、缓存与临时输出保留在仓库外。公开精简证据应先校验来源、检查敏感内容并说明缺失范围；不能因某个归档已在Git中就继续扩大上传范围。当前已有归档/视频本轮不删除、不重上传；若后续要迁移到外部制品存储，须提供逐文件哈希映射和单独审查方案。

`.gitignore`只防止未来误加入，不能清除已经提交的文件或修复历史泄露。若发现真实密钥，应先单独处理凭证轮换与访问风险；任何改写历史必须另获授权，本轮不执行。

## 维护验证

`scripts/audit_repository.py`只读解析源码和Git跟踪清单，不执行下载器、模型、仿真或资源申请。`--check-docs`检查本地Markdown文件链接，不能验证外网链接、标题锚点、运行时路径或外部部署资产。脚本索引的测试关联属于静态证据，不能当作覆盖率。

完整G2测试需要未入库的专家与物理轨迹。公开轻量子集与静态检查只能证明对应接口；需要集群、模型或GPU的检查应报告`NOT_EXECUTED`及原因，而不是安装大型环境或申请GPU补证。

## 删除与迁移

本次没有推荐立即删除的文件。未来候选需逐一列出：内容哈希、当前调用者、测试引用、冻结清单/报告引用和替代位置。只有确认冗余并获得单独批准后才删除或移动；不因为`v2`/`v5`、重复哈希或无静态调用就认定无用。
