# 接触预载保持整合进一次性 Aloha→ARX 综合实验的评估

> 本文记录 `db1ceb9` 时的接口评估。后续集中 CPU 修复、正式候选及新增受限左臂接近修正见 [最终集中 CPU 审查](g2_final_concentrated_cpu_review.md)；本文的“只改变夹爪”“未生成候选”等描述仅适用于当时版本。

可以作为 **Aloha 原生执行器的控制协议干预** 整合，保留现有一次分配、一个模型服务、10 个试次与原顺序。它不会给 ARX 自动增加新的保持层，也不能替代模型产生右手接管动作。

本次审查发现并修复了两个 CPU 可发现的阻塞：负闭合预载下的最终开爪被保持逻辑卡住；候选模块未被发布脚本列入依赖。修复后固定作者控制器的 H50/K31 接口重放通过。完整物理交接和后续模型闭环仍未验证，因此本报告不构成提交授权或最终 GPU 发布验收。

## 模型动作执行的边界

原链路仍是 `g2_episode.run_episode → native_prefix → NativeBackend.execute → Base_Task.take_action(qpos) → Robot.set_arm_joints/set_gripper → SceneClock`。

- 50×14 原始输出不改写，前缀选择、关节排序、限位检查、动作预算和重新查询规则不变。
- 两臂 12 个关节的 TOPP 位置/速度驱动不经过预载选择器。候选在每个物理步只处理两侧夹爪驱动；没有加入等待段、额外动作或自动重试。
- 模型闭爪请求仍到达作者的 `set_gripper()` 并更新其逻辑命令缓存。确认持有后，更深闭合对应的实际位置驱动会被保持、速度前馈置零，这是有意的控制干预，**不能称为 14 维动作原样执行**。
- 下一次模型观测仍使用原生逻辑命令缓存及原观测定义，不把保持驱动伪装成模型输出。真实图像和物理状态会因控制干预改变，因此不能要求后续预测块与旧轨迹或另一窗口逐元素相同。
- 原 `CheckedFirstExchange` 的初态、首个请求及首块预测哈希门禁保留。它检查首次运动前的可比性；不是约束后续闭环必须相同。

## 发现的释放阻塞与最小修复

作者 `Robot.set_gripper()` 对开爪使用当前应用驱动计算归一化起点，每步最多向外推进 0.1。若首次持有时位置驱动为 −10 mm，模型请求开到 1，第一步原控制器输出 −4.5 mm，随后才会跨越物理闭合端点 0。

`f95b8bb` 的保持逻辑先将驱动裁成物理开度再判断释放。−10→−4.5 mm 的裁后开度均为零，故被恢复为 −10 mm；下一步又从 −10 mm 起算。结果是模型开爪请求已经消费，右手仍保持持有，后续请求也无法推进。

这条路径在合法的负预载范围内发生，不是模型缺少开爪预测，也不是碰撞阈值或接触门禁误报。H50 seed1 的原 3 cm 抬升使用正预载，不能覆盖该反例。

修复仅将**朝外的驱动变化**与**形成正物理开度**分开：

1. 沿既有夹爪标定方向识别向外变化，允许原控制器继续放松负预载，记录为 `relaxing_preload`。
2. 负预载放松本身不授权 releasing、不清除持有/锚点；失去接触或滑移仍触发原保护。
3. 真正增加物理开度时，原 `NativeReleaseTracker.guard_opening()` 和 `authorize_opening()` 继续决定是否允许释放。左手在没有右手确认时仍被拒绝。
4. 更深闭合仍保持锁存预载；没有修改力限、刚度、阻尼、接触阈值、锚点或成功判据。

发布依赖清单 `g2_final_prepare_review.RUNTIME_MODULES` 同时加入 `g2_native_preload`，防止重打包后在首次配置验证/执行时缺模块退出。旧冻结包和旧哈希未改动。

## 建议的同一次分配整合方式

保持现有名单及顺序，避免改变窗口、控制器和本体后又引入新的试次组合：

| 原顺序 | 条件 | 候选开关 |
| --- | --- | --- |
| 1–4 | seed0 H50、seed0 K31、seed1 K31、seed1 H50 | 全部启用同一修复版保持协议 |
| 5、8 | seed0 W4、seed1 W4 原生对照 | 同样启用，保持每个 seed 的源本体配置一致 |
| 6、7 | seed0 / seed1 ARX W4 策略 | 不叠加该开关，保留既有力控、映射、规划和恢复 |
| 9、10 | seed1 / seed0 ARX 修复专家 | 不变，仍是独立专家诊断 |

配置草案逐字段检查：仅 6 个 Aloha 配置新增 `native_preload_control`，其余字段不变；同 seed 的 H50/K31/W4 除窗口及标签外一致。ARX 和专家配置不变。[机器可读评估](../research/g2/preload-unified-integration/proposed-integration.json)

H50/K31 因而仍是同控制协议下的窗口比较。W4 原生/ARX 保留相同窗口，但机器人控制接口本来就不同，不能将结果差异全部归因于形态。与旧 GPU 的保持关闭结果只能称历史对照；当前 10 项不包含同时段的保持开/关因果对照，不能宣称隔离了保持方案的 GPU 因果收益。没有为此追加作业或试次。

每个试次仍独立重置场景和策略 RNG，保持实例也随 backend 重新创建；源本体的持有状态不会传到 ARX。共享的是冻结模型服务，不是物理状态。原准入、清理凭证、预期试次失败后的继续条件和真实危险导致全场停止的规则不变。

## 发布前仍要明确的内容

- 新版发布包需重新构建、校验新增模块依赖、六个开关、plan/config 绑定及全部哈希，不能复用旧授权或拿旧包替换。本轮只提交评估与修复，未生成新提交授权或 GPU 候选压缩包。
- 后续汇总必须明确报告模型闭爪请求、原控制器请求驱动、最终应用驱动、`holding_preload/relaxing_preload/release_requested`、双指持有及托盘支撑。现有 raw 事件已经保存这些量，但旧汇总器没有完整汇总新保持模式，不能把 close request 当作真实夹紧。
- 原 `check_success()` 保持原定义；同时独立列出成功判据返回时的实际接触、开度和支撑证据。特别是逻辑开爪缓存不是实际两指已分离的证明，不能以控制命令替代完整物理释放证据。
- 真实首请求/首块哈希、长时持有、原模型后续接管、完整物理释放及 ARX 策略收益仍需验证。CUDA/真实模型和渲染检查若获准，必须放在同一次 allocation 开头，不单独申请 smoke test；能继续用 CPU 做的物理验证不应标为只有 GPU 才可做。
- 原资源草案为单次 7 h、10 项单试次时限及原动作/物理步预算。候选不增加动作或等待段，但更晚失败可能比历史早停耗时更长；不能直接把旧早停耗时外推为新整场预计值。硬上限不扩大，当前报价和新的包授权仍需提交前复核。

原 seed0 的碰撞发生在持有前，候选不会消除它；ARX 源代理碰撞/规划问题也不会因为原生保持改善而自动解决。候选只改变夹爪执行协议，不生成右手接管动作、不注入专家后缀，不保证原模型完成任务。
